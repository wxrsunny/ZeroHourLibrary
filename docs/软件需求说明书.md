# 《零点借阅室》软件需求说明书

版本：验收同步 v1.0（开发前需求 v0.3 见 Git 历史）  
开发方式：单人开发  
课程方向：交互式剧情探索与多分支决策系统  
当前阶段：应用已完成构建、安装、23 项模块测试与 13 项模拟器检查。需求初版已于代码实现前提交，当前文档同步最终实现。

## 1. 项目定位

制作一款在鸿蒙手机模拟器运行的二维俯视角探索游戏。玩家通过屏幕方向键控制角色在房间内自由走动，接近物件后调查，收集线索、解开谜题，并通过最终选择影响结局。背景为即将闭馆的图书馆，目标是寻找一封未送达的信。

核心创意是“回声”：在同一个场景切换“现在”与“过去的回声”，查看不同的文字描述和可交互物件。此机制使用场景状态与条件判断实现。

用户已确认：从零开始、单人完成、《零点借阅室》图书馆背景、二维俯视角、方向键控制角色自由探索、现在与过去的回声、四个房间、一个核心谜题、两个结局及温暖像素风。截止时间充裕；剧情细节在实现中保持此范围，出现影响体验的未确定事项先询问用户。

## 3. 首版功能范围

| 模块 | 功能与约束 |
| --- | --- |
| 主菜单 | 新游戏、继续游戏、玩法说明；无有效存档时禁用继续游戏 |
| 自由移动 | 屏幕四向按键控制角色走动；支持按住移动；角色不能穿过墙壁、书架等障碍物 |
| 场景探索 | 前台、书架区、阅览区、旧资料室四个小场景；走到门口切换场景；靠近物件后出现调查提示 |
| 回声切换 | 在允许切换的场景观察现在与过去；不同状态呈现不同线索 |
| 线索手册 | 收集约五条关键线索；展示名称、描述和发现位置；重复调查不重复收集 |
| 核心谜题 | 一个密码谜题；从线索推导答案；输入错误可重试，输入正确后解锁后续探索 |
| 剧情选择 | 最终选择与关键线索共同决定两个结局；必须存在实际条件分支 |
| 存档恢复 | 完成关键操作后自动保存，退出并重启后恢复当前位置、线索和剧情进度 |
| 重新开始 | 先确认再重置当前进度；保留已经解锁的结局记录 |

首版只做一个故事章节、一个自动存档和两个结局。每个房间采用固定视口的二维俯视地图，通过角色位置、距离判断、障碍碰撞及门口触发实现自由探索。首版不引入相机滚动，以控制开发规模。

## 4. 玩家操作流程

主菜单 → 方向键控制角色走动 → 靠近物件并调查 → 查看回声 → 收集与核对线索 → 解开谜题 → 走到门口进入旧资料室 → 作出最终选择 → 查看结局。

玩家可在探索过程中查看线索手册，并在关闭应用后使用“继续游戏”恢复进度。

剧情门槛使用明确状态控制。例如，取得必要线索且密码正确后才允许打开资料室；缺少条件时给出可理解的提示。

## 5. 总体结构与模块接口

采用“页面与组件—游戏逻辑—本地存储”三层结构。

| 模块 | 职责 | 主要实际接口 |
| --- | --- | --- |
| StoryData | 定义场景、物件、线索、提示与结局文案 | getScene、getClue |
| WorldController | 管理角色坐标、移动、地图边界、障碍碰撞、调查距离与场景门口 | movePlayer、canStand、nearbyObject、distanceToRect |
| GameEngine | 判断调查条件、修改进度、验证谜题与决定结局 | investigate、submitPuzzle、canFulfilPromise、chooseEnding、objective |
| SaveRepository | 加载、校验、保存和重置进度 | load、save；新游戏使用 createProgress |
| 页面与组件 | 呈现场景、收集输入、反馈操作与保存结果 | 主菜单、探索页、线索手册、结局页 |

具体函数签名与返回值见《系统架构》。回声切换由探索页修改 era，剧情条件由 GameEngine 检查。业务判断集中在 GameEngine，避免在界面中堆积剧情条件。

## 6. 数据结构与存储

采用显式类型的 SceneDefinition、MapObject、Point、ClueDefinition、InteractionResult、GameProgress 和 SaveEnvelope。

GameProgress 至少包含：当前场景、角色坐标、当前时代、已收集线索标识、已访问场景、谜题完成状态、关键选择、当前结局及已解锁结局。

SaveEnvelope 包含存档版本、更新时间和 GameProgress。本地存储采用 HarmonyOS Preferences，将可序列化的存档写入并执行 flush。

进入游戏时检查存档版本、场景标识、坐标和必要字段；无效角色坐标回退至安全出生点。存档无效时提供说明和重新开始入口。写入失败时明确提示，不能显示虚假的“保存成功”。移动过程不逐帧写盘，在移动结束、调查、换房间等节点保存，并在应用进入后台时尝试保存。

## 7. 页面与交互设计

- 主菜单：游戏名称、简短引导、开始或继续入口。
- 探索页：场景标题、回声状态、二维地图与角色、四向移动按钮、附近物件调查按钮和线索入口。
- 线索手册：已发现线索及详情，提供返回探索入口。
- 结局页：结局名称、结果说明、已解锁结局和重新开始入口。

视觉设计以纸张、书页、索引卡和时间刻度形成统一风格。关键操作兼顾文字提示和状态变化，不只依赖颜色传达信息。首版使用原生布局与简单图形实现主要界面。

## 8. 验收标准

1. 能在指定鸿蒙手机模拟器编译、安装和启动。
2. 四个场景的移动与条件锁定均按设计生效。
3. 回声切换实际影响可见线索或物件交互。
4. 重复点击不会重复添加线索或破坏进度。
5. 密码错误保持未解锁状态，密码正确才推进剧情。
6. 两个结局可通过实际选择与条件分别到达。
7. 强制关闭并重新启动应用，能恢复先前的有效进度。
8. 重新开始需要确认，且不会误删结局收集记录。
9. 对游戏逻辑进行分支与存档场景验证，并区分逻辑测试、构建验证和模拟器实测结果。
10. 方向键能控制角色走动，离开按键后停止；墙壁和书架有真实碰撞，距离过远不能调查物件。
11. 从房间门口触发切换；进入新房间或恢复存档后，角色位于可行走区域。

## 9. 单人开发安排与交付

由同一开发者完成需求、剧情、界面、逻辑、测试和报告。GitHub 记录真实的阶段性开发修改，提交说明描述实际变化。

开发顺序：需求定稿 → 可编译工程与基础导航 → 探索及线索 → 谜题及结局 → 存档 → 模拟器验证 → 截图录屏与报告。

最终准备：需求说明书、完整源码、README、实际运行截图和录屏、Word 期末报告、GitHub 仓库链接与个人账号名称。截图与录屏须来自实际运行；姓名、学号待用户在报告阶段提供；实际验收证据见《测试与验收结果》。
